## 3. Generate a WorkflowAPI YAML from the example worker

The example worker lives at `src/temporal-local/worker/` and represents a B2B risk-enrichment service: 3 workflows, 12 activities, 1 task queue (`risk-enrichment`), namespace `B2B.RiskService`.

```bash
dotnet run --project src/temporal-local/worker -- --workflowapi-dump out/dump
```

**Expected output (last line):**

```
Wrote 1 documents to out/dump
```

Inspect:

```bash
ls out/dump
```

You should see:

- `risk-enrichment-risk-enrichment.workflowapi.yaml` — the WorkflowAPI document
- `index.json` — directory listing + global diagnostics

Open the YAML — you should see `bindings.temporal.namespace: B2B.RiskService`, `taskQueue: risk-enrichment`, 3 workflows under `workflows:` (including `RiskEnrichmentWorkflow` with its `Cancel` signal and `GetStatus` query), and 12 entries under `activities:`.

## 4. Render the generated YAML in the visualiser

The visualiser reads exactly one YAML at boot from `src/web/workflow-react-flow-visualizer-mvp/src/data/risk-enrichment.workflowapi.yaml`.

For the demo we swap the bundled hand-crafted file with our freshly generated one:

```bash
# Back up the bundled reference
cp src/web/workflow-react-flow-visualizer-mvp/src/data/risk-enrichment.workflowapi.yaml \
   src/web/workflow-react-flow-visualizer-mvp/src/data/risk-enrichment.workflowapi.yaml.reference.bak

# Drop in the generated document
cp out/dump/risk-enrichment-risk-enrichment.workflowapi.yaml \
   src/web/workflow-react-flow-visualizer-mvp/src/data/risk-enrichment.workflowapi.yaml
```

Run the visualiser:

```bash
npm --prefix src/web/workflow-react-flow-visualizer-mvp run dev
```

Open the URL Vite prints (usually `http://localhost:5173`). You should see the workflow graph rendered from the generated YAML — workflows on the canvas, activities as nodes, the Temporal binding badge showing the namespace + task queue.

When done, restore the reference file:

```bash
mv src/web/workflow-react-flow-visualizer-mvp/src/data/risk-enrichment.workflowapi.yaml.reference.bak \
   src/web/workflow-react-flow-visualizer-mvp/src/data/risk-enrichment.workflowapi.yaml
```

## 5. What's known to differ from the hand-crafted reference

The generated YAML is intentionally minimal (hackweek scope). Compared to `risk-enrichment.workflowapi.yaml` already bundled with the visualiser:

| Field | Hand-crafted reference | Generated by tool |
|---|---|---|
| `info` block | Present (title, version, description) | **Omitted** — no source on .NET attributes |
| `host.name`, `host.owner`, `host.environment`, `host.baseUrl` | Present | **Omitted** — `host.id` only, derived from task queue |
| `host.id` | `risk-service` (semantic) | `risk-enrichment` (== task queue — hackweek deviation) |
| `bindings.temporal.webUrl`, `workerHost` | Present | **Omitted** — no source in DI registration |
| Workflow `displayName`, `summary`, `version`, `tags` | Present | **Omitted** — no source on `[Workflow]` attribute |
| Workflow `run.input` / `run.output` `$ref` | JSON schema refs | **Omitted** — Phase 2 (requires JSON Schema generation) |
| Workflow `subflows`, `childWorkflows` | Present | **Omitted** — Phase 2 (call-edge detection) |
| Activity `title`, `summary`, `group` | Present | **Omitted** — no source on `[Activity]` attribute |
| `bridges` (Nexus) | Present | **Omitted** — Task 12 (deferred for hackweek) |
| `components.schemas` | Full JSON schemas | **Omitted** — Phase 2 |

These omissions are tracked under `.squad/decisions/inbox/` as Deviation Records and in the hackweek tech-debt log.

## 6. What to talk about during the demo

1. **The tool runs against the user's real Temporal worker** — no separate config file, no spec maintenance. The user's `Program.cs` and the `[Workflow]`/`[Activity]` attributes ARE the source of truth.
2. **Discovery is bidirectional** — the scanner finds attribute-decorated classes; the DI options reader finds what the host actually registered. Mismatches surface as `WF001`/`WF002`/`ACT001`/`ACT002` diagnostics.
3. **Output is deterministic** — re-running the dump produces byte-identical YAML, so the document is safe to commit and code-review.
4. **The same YAML feeds the existing visualiser unchanged** — proves the bridge between .NET source and UI works end-to-end.
5. **Everything generated is a strict subset of the WorkflowAPI spec** — nothing in the document is invented; richer metadata (Info, schemas, bridges, call edges) are explicit Phase 2 work.

## 7. Quick troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `Wrote 0 documents` | Worker has no `AddHostedTemporalWorker(...)` | Confirm `src/temporal-local/worker/Program.cs:ConfigureServices` matches a real registration |
| `WF001` warnings in `index.json` | `[Workflow]` class exists but no `AddWorkflow<T>()` for it | Either register it or remove the attribute |
| `WF002` warnings | `AddWorkflow<T>()` for a type the scanner couldn't see | Confirm the type's assembly is loaded; check it's reachable from the registered worker types |
| Visualiser shows the original sample, not the generated one | Browser cached the old YAML | Hard-refresh (Cmd+Shift+R) or restart Vite |
| Visualiser blank / errors | Generated YAML is missing a field the visualiser hard-requires | Check the browser console — file a deviation note and either widen the visualiser or extend the factory |
